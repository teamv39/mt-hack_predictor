## 1. Концепция и продуктовая суть

Мы разрабатываем не просто прогноз времени прибытия (ETA), а **проактивную Систему Поддержки Принятия Решений (СППР / DSS)** для диспетчеров городского транспорта (Дептранс Москвы / Мосгортранс / ЦОДД).

* **Главная боль города:** «Пачкование» автобусов (*Bus Bunching*) и схлопывание интервалов (*Headway collapse*) — когда пассажиры ждут 25 минут, а затем приходят 3 автобуса подряд.
* **Наше решение:**
  1. **Предикт за 15–40 минут:** ML заранее выявляет зоны риска деградации интервалов.
  2. **Объяснимый ИИ (XAI):** Факторный анализ на базе SHAP показывает причину (затор на перегоне, задержка посадки из-за дождя, светофор).
  3. **Actionable UI (Готовое действие):** Кнопка прямого действия для диспетчера: *«Придержать борт №1043 на 2.5 мин на остановке Х»* (стратегия *Holding*), предотвращающая сбой до его наступления.

## 4. Команды для работы и проверки сборки

### Go Backend:
```bash
cd backend
go run ./cmd/server         # Запуск сервера на :8080
go test ./...               # Запуск тестов
go build -o bin/server ./cmd/server # Проверка компиляции
```

### Frontend (React + Vite):
```bash
cd frontend
npm install                 # Установка зависимостей
npm run dev                 # Запуск dev-сервера на :5173
npm run build               # Проверка production-сборки
```

### ML & Data (uv / Python):
```bash
cd ml
uv sync                     # Установка зависимостей в venv
uv run uvicorn src.api.server:app --reload --port 8000 # Запуск сервиса предиктов
```

## 5. Правила и договоренности для кода

1. **Контракты превыше всего:** Любые изменения форматов телеметрии или алертов согласуются и сразу вносятся в [backend/internal/models/types.go](file:///Users/shteppinson/dev/hacks/mt-hack_predictor/backend/internal/models/types.go) и [docs/api_contracts.md](file:///Users/shteppinson/dev/hacks/mt-hack_predictor/docs/api_contracts.md).
2. **Продакшн-мышление:** Избегать "игрушечного" кода. Бэкенд должен выдерживать высокую частоту обновлений телеметрии.
3. **Объяснимость обязательна:** Каждая рекомендация модели должна сопровождаться SHAP-факторами (почему система приняла такое решение).
4. **Валидация во времени:** В ML строго использовать `TimeSeriesSplit`, заглядывание в будущее недопустимо.
5. **UI-стандарты:** Тёмный строгий дизайн Ситуационного центра ЦОДД (`#0B0F17` / `#0F172A`), парящие полупрозрачные панели, микроанимации и четкие цветовые маркеры (зеленый/желтый/красный).

### 6.1. Критически важные документы (MUST READ перед каждой задачей)

Перед внесением любых изменений в код агент **ОБЯЗАН** прочитать и учесть следующие документы:

| Приоритет | Документ | Когда читать | Путь |
|-----------|----------|--------------|------|
| 🔴 P0 | **Implementation Plan** | Всегда | `docs/implementation_plan.md` |

| 🟡 P1 | **Domain Models (types.go)** | При изменении структур данных | `backend/internal/models/types.go` |
| 🟡 P1 | **Product Backlog (MoSCoW)** | При завершении задачи или добавлении фичи | `docs/product_attacks_and_backlog.md` |

### 6.2. Правила синхронизации документации

1. **Изменил API → обнови контракт.** Если добавлен/изменён/удалён эндпоинт, WebSocket-сообщение или структура модели — немедленно обновить `docs/api_contracts.md` и `backend/internal/models/types.go`.
2. **Завершил задачу → отметь в плане.** После завершения любой задачи из Phase 7 (или новой) — поставить `[x]` в `docs/implementation_plan.md` и обновить таблицу готовности.
3. **Добавил сервис или изменил инфраструктуру → обнови архитектуру.** Любые изменения в `docker-compose.yml`, новые микросервисы, изменения в сетевой топологии — отразить в `docs/architecture.md` (включая Mermaid-диаграммы).
4. **Реализовал фичу из бэклога → обнови MoSCoW-чеклист.** Отметить выполненное в `docs/product_attacks_and_backlog.md`.
5. **Создал новый документ → добавь в индекс.** Любой новый `.md` в `docs/` должен быть добавлен в таблицу быстрых ссылок `docs/index.md`.
6. **Не удалять и не затирать существующую документацию.** Можно дополнять, уточнять, исправлять фактические ошибки — но нельзя молча удалять секции или документы.

### 6.3. Порядок работы агента (Workflow)

```
1. Получил задачу от пользователя
2. Прочитал docs/implementation_plan.md (текущий статус, что уже сделано)
3. Прочитал релевантные P0/P1 документы (контракты, архитектура)
4. Создал ветку от актуального dev (git checkout dev && git pull && git checkout -b feat/...)
5. Выполнил задачу в коде
6. Обновил все затронутые документы (контракты, план, чеклист)
7. Проверил сборку (make check)
8. Запушил ветку и слил в dev (или открыл PR в dev)
```

## 7. Регламент работы с Git (Git Flow)

> **КРИТИЧЕСКИ ВАЖНОЕ ПРАВИЛО:** Все разработчики и AI-агенты работают **ТОЛЬКО от ветки `dev`**. Прямые коммиты и пуши в `main` **СТРОГО ЗАПРЕЩЕНЫ**. `main` используется исключительно для финальных стабильных релизов на защиту.

### 7.1. Правила ветвления
1. **Базовая ветка:** Все ветки создаются строго от актуального `origin/dev`:
   ```bash
   git checkout dev
   git pull origin dev
   git checkout -b <prefix>/<short-description>
   ```
2. **Именование веток (префиксы):**
   * `feat/<name>` — новая фича или компонент (например, `feat/ndtp-tcp-receiver`, `feat/catboost-training`, `feat/inspector-card`).
   * `fix/<name>` — исправление бага или ошибки в логике (например, `fix/websocket-reconnect`).
   * `docs/<name>` — добавление или актуализация документации.
   * `refactor/<name>` — рефакторинг без изменения внешнего API.
   * `chore/<name>` — обновление зависимостей, Dockerfile, Makefile.

### 7.2. Чеклист перед коммитом и пушем
Перед каждым коммитом и пушем агент **ОБЯЗАН**:
1. Запустить `make check` (проверка компиляции Go и сборки Vite). Никаких сломанных билдов!
2. Проверить `git status` — никаких лишних тяжелых файлов (датасеты, логи, бинарники).
3. Написать осмысленное сообщение коммита по Conventional Commits:
   * `feat(backend): add NDTP TCP listener on port 9201`
   * `fix(ml): resolve process substitution syntax in Dockerfile`
   * `docs(plan): update Phase 7 roadmap with official case criteria`
4. Запушить ветку в `origin`:
   ```bash
   git push -u origin <имя-ветки>
   ```
5. Слить в `dev` (или создать Pull Request в `dev`):
   ```bash
   git checkout dev
   git pull origin dev
   git merge --no-ff <имя-ветки>
   git push origin dev
   ```

### 7.3. Запрещенные действия
* ❌ Коммитить или пушить напрямую в ветку `main`.
* ❌ Делать `git push --force` в `dev` или `main`.
* ❌ Добавлять тяжелые файлы (> 10 МБ, `.tar`, `.csv`, `.parquet`, модели) в Git в обход `.gitignore`.
